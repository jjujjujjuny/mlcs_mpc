- **"각속도 묶인 서보 3.2 rad/s" 가 잘 맞은 이유**: 실차는 노드가 명령 자체를 3.2 rad/s 로 묶는다 (5 번). 서보 물리 속도와 별개 — 시뮬에서도 노드 쪽 묶음을 따로 두고, 물리 서보는 계단 응답 측정 뒤 정하는 게 맞다.
- 상태 → 명령: mocap stamp 에서 /drive 까지 ≈ 전달 3 + (타이머 위상 0~33, 평균 17) + 풀이 24 ≈ 평균 40 ms (메인 PC 실측 30~35 ms 와 같은 범위).
- 젯슨 (Orin) 과 맥북은 풀이 시간이 다르다 → **맥에서 실제로 푼 시간 대신 위 분포에서 표본을 뽑아 지연으로 주는 모드**를 권함 (그래야 '실차와 같은' 타이밍).

## 2. 시뮬에 넣을 순서 제안

1. `env/estimation.py`: PoseKF 를 그대로 (mocap 측정 잡음 r 1e-4 ≈ 1 cm 표준편차, 실측 mocap 잡음은 이보다 작음)
2. `env/timing.py` 사건 큐: mocap 100 Hz (간격·전달 분포 표본) / VESC 상태 50 Hz / 제어 30 Hz 타이머 + 풀이 시간 표본 + pending 건너뛰기 / 명령 도착 즉시 적용
3. 조향: 노드 묶음 3.2 rad/s (명령) + 물리 서보 (측정 전엔 τ 0.04~0.06 또는 각속도 묶음 후보)
4. 바퀴: wheel_speed_tau 0.4 (또는 v2 drivetrain 모델), ws_dec 2.5
5. `--realtime` 끔 ↔ 켬 비교 + `sim_fidelity.py` 로 11-10 주행 재생 → 1 s 오차가 실측 분포를 넣었을 때 줄어드는지

- 실차 시험 없이 바로 확인할 거리: 칼만 필터 가짜 vy 가 시뮬 폐루프에서 코너 바깥 쏠림을 재현하는지 (실차에서 본 것).
- **연구 쪽 첫 개선 후보**: mocap 에서도 r 을 KF 대신 자이로 (`wheel_odom /odometry/filtered`, 바이어스 뺀 VESC IMU) 로 — 대회 때 lidar_bridge 에서 같은 문제 (KF r 110 ms 늦음) 를 이걸로 고쳤다 (af48e21). 시뮬에도 '자이로 경로' 를 선택지로.
