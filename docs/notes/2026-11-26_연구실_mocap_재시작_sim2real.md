## 1. 시뮬 ↔ 실차 비동기 구조 정리 (11-24)

서용화 연구원님이 맥북에서 실차와 거의 같은 시뮬을 원하심 → 젯슨 실측으로 실차 신호 흐름을 숫자로 정리해 메인 PC 에 넘김 (`data/timing/jetson_mocap_20261110.json`, 11-10 연구실 mocap 24 주행).

| 단계 | 실측 (중앙 / p95 / p99) |
|---|---|
| mocap 새 위치 간격 | 10.0 / 12.1 / 15.2 ms |
| 전달 (측정 → 브리지) | 2.7 / 5.6 / 7.6 ms |
| 풀이 (30 Hz, 비동기, 답 없으면 그 주기 건너뜀) | 23.8 / 26.3 / 38.5 ms |
| /drive 도착 간격 | 33.3 / 37.7 / 68.3 ms |
| VESC 상태 | 20 / 30 ms |

- mocap 칼만 필터가 vx·r 을 80~90 ms 늦게 냄 (메인 PC 재생 검증) — 오늘 속도 상태를 센서로 바꾼 이유
- 맥은 풀이 속도가 달라 '젯슨 분포에서 뽑은 지연' 모드를 권함

## 2. 기준점: 앞바퀴 축 (연구원님 결정)

- 처음엔 '/mpc/state 는 뒤축 유지, MPC 안에서 변환' (A) 을 제안했지만 결정은 **B: mocap 도 앞축으로 보내고 수식도 앞축, 변환 없음**
- 젯슨 hmpc (무게중심 모델) 는 make_state 를 '기준점 → 무게중심 거리' 로 일반화 (뒤축 +lr, 앞축 lr − L). race.sh 가 source 로 정함 (mocap → 앞축, lidar → 뒤축). 시험 15 개 통과 (앞·뒤축으로 같은 차 → 같은 OCP 상태)
- 속도 상태 vy (기구학) = 뒤축 미끄럼 0 → 앞축 옆속도 L·r

## 3. 새 마커 보정 — straight 보다 spin 좌우가 정확

- 첫 spin 은 원 피팅 잔차 352 mm (조향을 끝까지 유지 못 함) → 버림. mocapcal 이 조이스틱을 안 띄워 몰 수 없던 것도 고침
- straight 두 번: +1.4°·+1.6° 였지만 스틱 중립인데도 2.75 m 에 36 cm 휘어 감 → 덜 믿음
- **spin 좌·우 한 번씩:** 두 회전 중심은 뒤축 연장선 위 좌우 대칭이라 두 벡터 차이가 차체 옆 방향을 가리킨다 → 남은 기울기 −2.47° → yaw_offset 4.0°. 보정하면 좌우 x 가 0.3155 m 로 정확히 같아짐 (검산). 회전 반경 좌우 0.797 m
- 확인 spin: 예측 0.3155 vs 측정 0.3230 m (산포 1.9 cm 안)
- 교훈: '곧게 밀기' 는 사람 정확도에 달렸고, 좌우 원은 기하가 스스로 검산해 준다

## 4. 서보 계단 응답 (`./drive.sh servostep /wheel/pose`)

- 앞바퀴에 강체 (마커 3 개) → 실제 조향각 = 바퀴 yaw − 차체 yaw. 서보 값을 직접 내서 노드의 3.2 rad/s 묶음 없이 물리 서보만
- 1 차 측정은 왼쪽이 1/3 만 꺾이고 0 복귀가 안 되는 것처럼 보였는데 **바퀴 강체가 카메라 시야를 벗어난 탓** (기구 이상 아님). 2 차는 추적 끊김 0
- 정상상태 ±0.2 → ±0.21, +0.4 → +0.305 / −0.4 → −0.372 (한쪽 바퀴라 애커만 섞임)

| 모델 | rms (mrad) |
|---|---|
| 지연 40~60 ms + 각속도 상한 2.0~2.5 rad/s | **16.7** |
| 지연 60 ms + 1 차 80 ms | 19.5 |
| 지금 MPC (1 차 0.13, 지연 0) | 27.1 |
| 메인 PC 시뮬 (1 차 0.03) | 57.5 |

- 노드의 명령 변화율 묶음 3.2 rad/s 보다 물리 서보 (2~2.5) 가 느리다 → 실차 병목은 서보

## 5. 바퀴 계단 응답

- 거치대 (`./drive.sh speedstep`, 제가 직접 실행): 지연 80~120 ms, 10→90 % 0.16~0.4 s, 정상상태 −4~5 % (새 PID ki 낮음), 0 에서 출발이 두 배 느림
- 땅 위 (O자 주행 4 개, `./drive.sh actuator`): **1 차 τ 0.40 그대로** (RMSE 0.106), 상한형 τ 0.25 · 가속 ≤ 2.0 · 감속 ≤ 3.75. 무부하 거치대 값은 땅 위보다 훨씬 빠르니 시뮬엔 땅 위 값

## 6. O자 트랙 (메인 PC `tools/make_o_track.py`, 12.3 m, 길 폭 0.50, R 1.0)

- 길 폭이 좁아 wall_margin 0.28 이면 통로가 없다 → 0.10 (무게중심 ±11~14 cm)
- **첫 주행 실패:** 메인 PC 설명은 '반시계' 인데 파일은 **시계 방향** (곡률 음수). 차를 반시계로 둬 μ +177° → 0.5 m 길에서 돌아서려다 교착 3 번 → 정지. 같은 주행에서 hmpc.launch 가 mocap_bridge 를 직접 띄우는 경로라 wheel_odom 이 안 떠 자이로가 0 → 고침
- 그 뒤 v_max 1.0 → 3.0:

|---|---|---|---|---|---|

## 배운 것

- **기준점·좌표 약속을 먼저 정한다.** 위치 기준점 (뒤축 → 앞축) 하나가 브리지·모델 변환·옆속도·보정 도구·로그 분석에 다 걸린다
- 측정이 이상하면 장치보다 **측정 경로** (카메라 시야, 방향 약속) 부터 의심한다 — 서보 1 차, O자 첫 주행 모두 그랬다
- 거치대 값과 땅 위 값은 다르다 (바퀴 τ 0.05~0.2 vs 0.4). 시뮬엔 땅 위 값을 쓰고 거치대는 변화 감지용으로
- 필터 지연은 저속에선 안 보이고 속도가 오르면 랩타임·횡오차로 드러난다 (v1.0 같음 → v2.0 −8.5 %)
