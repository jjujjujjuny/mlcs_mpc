## 1. 배경 및 목적

지금까지는 젯슨에서 RViz 와 터미널을 띄우고 NoMachine 으로 젯슨 화면 전체를 메인 PC 에서 봤다. 대회에서는 노트북 1, 공유기 1(인터넷 없음, IP 고정 가능), 젯슨 1 로 해야 한다. 조건(사용자):

1. 주행 중 노트북에서 차 상태를 실시간으로 본다
2. 화면 공유처럼 큰 데이터는 안 된다 (주행 방해)
3. 젯슨 CPU 에 부담이 크면 안 된다
4. 젯슨 RViz 토픽을 노트북 RViz 로 본다

지난 대회에서 큰 공유기를 가져온 팀 때문에 다른 팀들이 RViz 버벅임 → 차 상태 끊김 → 자율주행 차가 벽에 박음 → 조이스틱도 안 됨을 겪었다고 한다. 이번 대회는 소규모라 방해 대응까지는 하지 않기로 했다 (사용자 판단). 다만 젯슨 ROS 를 localhost 로 묶은 것은 그 대응과 겹친다 (2절).

## 2. 방법

**왜 Zenoh 브리지인가**

- 화면 대신 토픽만 보낸다. 무엇을 몇 Hz 로 보낼지 브리지 설정 한 파일(`tools/zenoh/jetson.json5`)에서 정한다 (허용 목록 + `pub_max_frequencies`)
- 젯슨 DDS 는 localhost 에만 있다. 와이파이로 나가는 길은 브리지 TCP 하나라, 와이파이가 흔들려도 주행 노드끼리의 통신은 영향이 없다. 노트북을 DDS 로 직접 붙이는 방식(CycloneDDS 유니캐스트)은 와이파이 상태가 젯슨 DDS 에 섞이고, Humble FastDDS 동기 발행에서는 막힌 와이파이가 제어 루프의 `publish()` 를 붙잡을 수 있어 쓰지 않았다
- 같은 공유기의 다른 팀 ROS(도메인 0)와 섞이지 않는다. 섞이면 남의 `/drive` 가 우리 mux 로 들어온다
- 브리지는 자동 발견(멀티캐스트 scouting)을 껐다. 다른 팀 Zenoh 브리지와 붙으면 남의 `/initialpose` 가 우리 위치추정을 옮길 수 있다

**보내는 것** (`jetson.json5`)

| 젯슨 → 노트북 | 상한 |
|---|---|
| `/tf` `/tf_static` | 제한 없음 — 여러 노드가 한 토픽에 섞여 있어 솎으면 특정 변환이 통째로 빠진다 |
| `/map` | 0.5 Hz |
| `/scan` | 10 Hz |
| `/tracked_pose` `/mpc/state` | 20 Hz |
| `/mpc/predicted_path` 10, `/mpc/reference_path` 2, `/hmpc/status` 5, 마커들 5 | |
| 뺀 것 | `/trajectory_node_list` `/constraint_list` (맵 전체 노드, 33 Hz), `/viz/trail` (최대 2000 포즈를 매번) |

노트북 → 젯슨은 `/initialpose` 하나 (RViz 2D Pose Estimate).

**실행**

- 젯슨: `./race.sh` 가 브리지를 자동으로 함께 띄운다 (`MLCS_BRIDGE=0` 이면 끔). 따로는 `./drive.sh bridge`. `./drive.sh stop` 이 같이 내린다
- 노트북: `./car.sh`. 주행 화면(bench/race/term)은 젯슨 tmux `race` 세션 안에서 돈다 — 노트북 창을 닫거나 와이파이가 끊겨도 주행은 계속된다
- `MLCS_RACE_BENCH=1 ./race.sh` = race.yaml 의 `drive` 를 이번만 무시하고 bench (`car.sh bench` 가 쓴다). `drive: true` 설정으로 넣어 보고 `MLCS_HMPC_DRIVE=0` 이 되는 것 확인
- 노트북 연결 파일: `tools/zenoh/laptop.json5` (client, 젯슨이 없거나 끊겨도 죽지 않고 계속 재접속), `laptop.rviz` (대회 RViz 에서 Trajectory 표시만 끔)

## 3. 진행 상황

**젯슨 안에서 먼저 시험** (ROS 도메인 0 = 젯슨, 5 = 노트북 흉내, 브리지 2개를 localhost 로)

- `/scan` 40 → 9.9 Hz, `/tf` 100 Hz 그대로, `/initialpose` 역방향 전달, 목록 밖 `/constraint_list` 차단
- 고친 것: ① 노트북 브리지는 기본값이 "첫 접속 실패 시 종료" → `connect.exit_on_failure: false`, `timeout_ms: -1` ② `drive.sh bridge` 의 "이미 떠 있다" 검사가 명령줄에 그 단어가 든 셸까지 잡음 → 실행 파일 경로로만

**노트북 브리지 실행 파일** — 공식 x86_64 빌드는 둘 다 Ubuntu 22.04 노트북에서 안 떴다

| 시도 | 결과 |
|---|---|
| x86_64 gnu standalone 1.10.2 | ✗ `GLIBC_2.38 not found` (노트북 2.35) |
| x86_64 musl standalone 1.10.2 | ✗ musl 동적 링크라 `/lib/ld-musl-x86_64.so.1` 필요. 우분투 libgcc_s 를 섞으면 `_dl_find_object` 없음 |
| **소스 빌드** (태그 1.10.2, `cargo build --release -p zenoh-bridge-ros2dds`) | ✓ 2분 42초 (8코어), 요구 glibc 2.34. `clang`·`libclang-dev` 필요 (없으면 bindgen `stddef.h not found`) |

젯슨 aarch64 gnu 공식 빌드는 GLIBC 2.30 까지만 요구해서 그대로 쓴다. 실행 파일(각 26 MB)은 레포에 넣지 않는다 (`tools/zenoh/.gitignore`).
