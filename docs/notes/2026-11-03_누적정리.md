- 작성일: 2026-11-03
- 대상 기간: 2026-09-14 ~ 2026-11-02 (커밋 54건)
- 저장소: `jjujjujjuny/mlcs_mpc`

## 1. 연구 배경 및 목적

### 배경

HyperMPC(arXiv:2508.06181)는 차량 동역학 모델의 파라미터를 고정값으로 두지 않는다. 신경망(HyperPM)이 예측 구간 전체의 파라미터 궤적을 내고, MPC가 그 궤적으로 미래를 예측한다. 저자들은 F1TENTH 규모 차량에서 고정 파라미터 모델보다 추종 성능이 좋아졌다고 보고했다.

본 연구실 차량은 저자들 차량과 휠베이스가 같다(0.33 m). 그러나 질량, 조향 한계, 노면, 실험 공간이 다르다. 따라서 논문 결과를 그대로 재현할 수 있을지는 우리 플랫폼에서 직접 확인해야 한다.

### 목적

1. 저자들의 정식화(`mpc_formulation_car.py`)를 우리 차량에 이식하고 실차에서 폐루프로 주행시킨다.
2. 고정 파라미터 동역학 MPC(논문의 비교 기준선)와 HyperMPC를 같은 트랙에서 비교한다.
3. 그 과정에서 필요한 차량 실측값, 실험 환경, 학습 데이터 수집 체계를 갖춘다.

### 단계 (`docs/ROADMAP.md`)

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 운동학 MPC + 모션캡처 위치추정 | 시뮬레이션 완료 |
| 2 | 실차 검증 + 데이터 수집 | **진행 중** |
| 3 | 동역학 모델 (Pacejka 타이어) | 오프라인 OCP 빌드까지 |
| 4 | HyperPM (시변 파라미터 신경망) | 대기 |
| 5 | HyperMPC 실차 주행 | 대기 |

## 2. 연구 방법

### 2.1 실험 플랫폼

| 항목 | 구성 |
|---|---|
| 차량 | F1TENTH 1/10, Traxxas 3351R Velineon (센서리스 BLDC), VESC |
| 연산 | NVIDIA Jetson (JetPack R36.5), ROS 2 Humble |
| 위치 | OptiTrack Motive 2.3 → NatNet 3.1 → `natnet_ros2` (100 Hz) |
| 조종 | Logitech F710 |
| 실험 공간 | 19각형 경계, 24.13 m², 5.78 × 6.74 m (mocap 월드 좌표계) |

### 2.2 위치·상태 추정

`Motive → /car/pose (100 Hz) → mocap_bridge → /mpc/state`

- `mocap_bridge`가 칼만 필터로 속도와 요레이트를 추정한다.
- 마커 지그의 Pivot을 앞축 위에 두고 `offset_x = −0.33`(= −휠베이스)으로 뒤축 기준 상태로 바꾼다.
- 원본 위치(`x, y, yaw`)를 함께 기록해 오프라인에서 다시 미분할 수 있게 했다. 논문은 Savitzky-Golay 필터로 오프라인 미분했다.

### 2.3 기준 제어기 — Stanley

배관(위치추정 → 제어 → 구동)을 검증하는 기준 제어기로 Stanley를 썼다. 곡선 구간 정상상태 오차를 없애기 위해 곡률 전방보상 항을 넣었다.

```
δ = k_head·θ_e + atan2(−k_e·e, k_soft + |v|) + k_curv·atan(L·κ)
```

### 2.4 캘리브레이션

모든 값은 **모션캡처로 측정한 실제 거동**을 기준으로 정했다.

- 속도 게인: 정속 주행에서 VESC ERPM과 mocap 속도를 비교
- 조향 게인·중립: 일정 조향으로 원선회해 반경을 재고 역산
- 최대 조향각: 서보를 직접 밀어 기계 한계를 찾고(`tools/servo_sweep.py`), 선회반경으로 확인
- 질량·무게중심: 저울로 전체 / 앞축 / 뒤축 하중을 측정
- 요 관성모멘트: 독립적인 두 추정식으로 교차 확인 (§3.3)

### 2.5 트랙 생성

- 원저자 파이프라인을 그대로 따른다: `x_m,y_m,w_tr_right_m,w_tr_left_m` 원본 → 저자 `TrackReader`(k=5, s=2.0, 5점/m) → `prep_*.csv` → `getTrackCustom`. 곡률·heading을 우리 방식으로 다시 계산하지 않는다.
- 트랙을 만드는 도구는 세 가지다: 손클릭(`drawtrack`), 해석적 생성(`stracks`), 수동 주행 기록(`laptrack`).
- 모든 트랙은 저장 전에 검사한다: 차량 선회 한계, 실험실 경계 포함 여부, 폐곡선 회전수(∮κds/2π), 저자 전처리 후 곡률.

### 2.6 학습 데이터 수집

`./drive.sh joy --log` — 조이스틱으로 수동 주행하면서 100 Hz로 기록한다.

- 시간축: mocap 스탬프 기준. 다른 센서는 그 시점의 최신값을 붙이고, 안 온 값은 빈칸으로 둔다.
- 기록 항목(논문 6.4.3과 같음): 위치·자세, KF 속도, 입력 명령, 모터 RPM·q축 전류·전류·듀티·전압, 서보 지령
- 목표: 36분 (논문 기준)

### 2.7 최적화 문제 (오프라인)

- acados SQP_RTI + HPIPM, CasADi
- 동역학: 저자 `casadi_car_model_naive.py` (Pacejka 단일트랙, torch 불필요)
- 상태 9개 `[s, n, μ, vx, vy, r, friction, ω, δ]`, 입력 2개, 파라미터 31개
- 예측 구간 N=80, dt=0.033 s (2.64 s)

## 3. 연구 진행 상황

### 3.1 수동 주행 지연 원인 규명 (9월)

수동 주행 지연을 Python 처리 지연으로 의심했으나, 측정 결과 원인은 아니었다.

| 구간 | 측정 |
|---|---|
| ROS 체인 (조이스틱 → 명령 발행) | 중앙 2.1 ms (80 Hz) |
| VESC 속도 응답 | 300~600 ms ← **원인** |

VESC Tool에서 센서리스 FOC 설정과 속도 PID를 조정했다. 이 결과에 따라 C++ 전환은 보류했다.

### 3.2 캘리브레이션 결과 (2026-09-30)

| 항목 | 보정 전 | 보정 후 |
|---|---|---|
| 속도 게인 `speed_to_erpm_gain` | 오차 −3.50% | **4781.5**, 오차 −0.81% |
| 조향 게인 | 좌우 비 1.3457 / 1.3982 | **−0.8845**, 비 0.9996 |
| 조향 중립 | −2.36° | **0.4909**, +0.10° |
| 최대 조향각 | 0.36 rad (가정) | **0.40 rad** (±0.42 명령 → +0.398 / −0.402) |
| 최소 선회반경 | 0.877 m | **0.781 m** (실측 0.776~0.785) |

- 기존 `calibrate.py`의 중립 보정식에 부호 오류가 있었다. 안내대로 적용하자 편차가 −2.36° → −5.35°로 오히려 커졌고, 식을 바로잡아 해결했다.
- 조향 부호를 확인했다: 양의 조향 = 좌회전 (ROS 관례).

### 3.3 차량 제원 (2026-10-02)

| 항목 | 값 | 근거 |
|---|---|---|
| 질량 | **3.097 kg** | 저울 (논문 차량 5.1 kg의 61%) |
| l_f / l_r | **0.1802 / 0.1498 m** | 앞축 1400 g, 뒤축 1685 g → 합 0.3300 = L |
| 하중 분포 | 앞 45.4% : 뒤 54.6% | 무게중심이 뒤쪽 |
| I_z | **0.084 kg·m²** (추정) | 균일 평판 0.0846, m·l_f·l_r 0.0836 — 두 식이 1% 안에서 일치 |
| μ | 0.35 (가정) | **미측정** |

**논문의 I_z = 0.46은 쓰지 않았다.** 5.1 kg에서 회전반경으로 환산하면 0.300 m인데, 길이 0.505 m 물체의 이론적 최댓값(0.253 m)을 넘는다. 측정치가 아니라 HyperPM 학습 파라미터의 초기값으로 판단했다.

### 3.4 기준 제어기 주행 (Stanley, track_5)

- 횡오차 표준편차 **0.95 cm**, 53.8초 연속 주행 (bag `20260930_220855`, 2692 샘플)
- 곡선 구간에서 −4.29 cm의 일정한 편차가 있었다. 지그 오프셋을 +4.3 cm 옮겨도 평균이 −4.20 cm로 그대로였으므로, 원인은 지그가 아니라 제어기의 곡률 정상상태 오차로 결론 내렸다. 곡률 전방보상(`k_curv`)을 넣어 해결했다.
- 곡률 추정 검산: ∑κ·ds = 6.282 (2π = 6.283)

### 3.5 HyperMPC 정식화 이식

- 저장소의 `mpc_formulation_car.py` 하나만으로는 정식화가 완성되지 않는다. 동역학·비용·파라미터를 받아 쓰는 `model` 파일이 없다. 그래서 OCP를 직접 세웠다(`hypermpc/offline_ocp.py`). 동역학은 torch 없이 쓸 수 있는 유일한 경로인 `casadi_car_model_naive.py`를 쓴다.
- acados 최소 OCP 스모크 테스트: `status = 0`, 풀이 시간 중앙 **0.659 ms**
- 전체 OCP는 코드 생성과 빌드까지 확인했다. 첫 빌드가 10분을 넘겨 시간 제한에 걸렸고, **풀이 시간은 아직 재지 않았다.**
- 원저자 `track_width: 0.25`는 **반폭이며 소프트 제약**이다. `casadi_car_model.py:106`이 `h = track_width ∓ n`을 log-barrier 비용으로 넣고, 상태 하드 제약(`lbx`)은 비어 있다.
- `I_z`, `l_r`은 우리 차 값으로 바꿨다. 나머지 8개(Cd0/1/2, I_e, K_fi, b1, b0, R)는 아직 논문 값이다.

### 3.6 트랙

**실험실 경계** — 19각형, 24.13 m², 최대 내접원 반경 2.08 m. 터틀봇 중심 궤적의 97퍼센타일로 만든 경계라 실제 벽보다 안쪽이다(보수적).

**기존 트랙 검토**

| 트랙 | 최소반경 | 주행 불가 구간 |
|---|---|---|
| track_1~4 (DeepRacer 기반) | 0.19~0.36 m | 31~42% |
| track_5 (해석적 스타디움) | 1.30 m | 0% ← 현재 사용 |

track_1의 곡률 제한 최적화는 250회 반복에서 수렴하지 못한 채 끝났다(`converged: false`). 요청값은 κ ≤ 1.2였는데 실제는 3.406이다.

**주요 발견: 저자 전처리가 선회반경을 줄인다**

저자 `TrackReader`(s=2.0)는 설계한 최소 선회반경의 **0.72~0.85배만** 남긴다. 2 cm 정도의 평활화 편차가 코너를 조이는 쪽으로 작용하기 때문이다.

| 설계 R_min | 전처리 후 |
|---|---|
| 0.90 m | 0.652 m |
| 1.10 m | 0.868 m |
| 1.45 m | 1.225 m |

따라서 차량 한계 0.781 m를 지키려면 **설계 단계에서 1.05 m 이상**으로 잡아야 한다. 또 원본 점 간격을 저자들과 같은 약 1 cm로 맞춰야 같은 평활화 결과가 나온다(5 cm면 RMSE 0.048 m, 1 cm면 0.022 m).

**레이아웃 검토**

- 직선 + S자 (`s_track`): 생성 완료. 설계 R_min 0.979 m → 전처리 후 0.845 m, 벽에서 경계까지 0.302 m
- 긴 직선 + U턴 + 대각선(요청 레이아웃): 해석적으로는 **이 실험실에서 만들 수 없음**을 확인했다. 회전 구간만으로 Δy가 3.5~4.7 m 생기고, 이를 되돌릴 수 있는 구간이 왼쪽 직선 하나뿐이다. 그래서 R ≥ 1.05 m에서는 닫히는 해가 없다.
- 결정: 원하는 라인을 **직접 수동 주행으로 기록**해 트랙을 만든다(`laptrack`). 차가 실제로 돌았으므로 선회 한계와 경계 조건이 자동으로 만족된다.

### 3.7 학습 데이터 수집

| 항목 | 상태 |
|---|---|
| 쓸 수 있는 누적량 | **0분** / 36분 |
| 2026-11-02 기록 (3.71분, 100 Hz, 끊김 없음) | 입력 열이 비어 있어 시스템 동정에 쓸 수 없음 |

- 위치와 VESC 내부 상태는 100% 기록됐다. 입력(`cmd_speed`/`cmd_steer`)은 0%였다. 로거가 MPC 쪽 입력인 `/drive`를 구독하고 있었기 때문이다. 실제로 차에 나가는 명령은 mux 출력인 `/ackermann_cmd`다. 수정했다.
- 속도 추정값의 상위 1%는 mocap 순간 튐으로 오염돼 있다(예: vy 최대 12.3 m/s). 중앙값은 모터 RPM 기준 속도와 맞는다. 원본 위치를 보존했으므로 후처리로 걸러낼 수 있다.

### 3.8 실험 인프라에서 확인한 문제와 조치

재발 방지를 위해 기록해 둔다.

| 문제 | 원인 | 조치 |
|---|---|---|
| 수동 기록이 0개 / 엉뚱한 궤적 | `/mpc/state`에 퍼블리셔 2개 → 두 궤적이 번갈아 기록됨 (시험용 퍼블리셔 잔존) | `checkstate`: 기록 전에 실제 데이터로 판정 |
| 노드 상태 조회 오류 | ROS 2 데몬·DDS 캐시가 죽은 노드를 계속 보고함 | 노드 확인은 프로세스(pgrep) 기준으로 |
| 기동 즉시 종료 | ROS 2가 빈 파라미터 값(`-p tag:=`)을 거부 | 값이 비면 인자 자체를 뺌 (네 번째 발생) |
| 종료 시 기록 유실 | SIGTERM에서 `finally`가 실행되지 않음, 버퍼 미기록 | 시그널 핸들러 + 5초마다 flush |
| Ctrl+C 후에도 스크립트 진행 | bash INT 트랩이 exit하지 않음, `ros2 run`이 신호를 노드에 넘기지 않음 | 공용 정리 함수, 자식 프로세스까지 신호 |
| Motive 연결 실패 | Motive PC 네트워크 미연결 (VirtualBox 가상 어댑터 IP 혼동) | 재연결 후 100 Hz 단일 궤적 확인 |

## 4. 향후 계획

### 4.1 바로 할 것

1. **학습 데이터 재수집** (`./drive.sh joy --log`) — 화면의 "명령 N%"가 100% 근처인지 확인하며 진행
   - 직선 가감속 + 타행: 구름·공기 저항(Cd0/Cd1/Cd2) 분리
   - 정상원선회 좌/우 대칭, 작은 원 한계(R≈0.9 m, 약 1.7 m/s): 타이어 특성
   - 8자, 슬라럼: 요 관성, 과도응답
   - 10분 단위로 나누고 태그를 붙여 기록
2. **오프라인 OCP 풀이 시간 측정** — 실시간 가능 여부를 가르는 숫자다. 30 Hz 제어면 예산은 33 ms다(논문은 x86 데스크톱에서 10.61 ms). 넘으면 N을 줄이거나 제어 주기를 낮춘다.
3. **수동 주행 기록으로 실험 트랙 확정** (`record` → `laptrack` → `preptrack`)

### 4.2 측정·보완

- μ(노면 마찰) 측정 — 원선회 속도를 단계적으로 올려 미끄러지기 시작하는 점을 찾음
- I_z 이선 진자 측정 (선택) — 줄 간격 0.10 m, 길이 0.8 m면 주기 약 5.9 s
- 수집 데이터의 상태공간 커버리지(vx–vy–r) 분석, 부족한 영역 보충
- 속도 이상치 필터링, Savitzky-Golay 오프라인 미분

### 4.3 정식화 → 실차

- 트랙 Frenet 변환, 횡편차 n 제약 ±0.25 적용
- OCP를 ROS 노드로 감싸기 (기존 안전 게이트, mocap 타임아웃, 수동 전환을 재사용)
- 고정 파라미터 동역학 MPC로 실차 폐루프 → Stanley 횡오차와 비교
- 파라미터 동정 (Pacejka 계수 등), 이후 HyperPM 학습 (torch + l4casadi)
  - 저자 학습 가중치(W&B 아티팩트)는 접근이 안 될 가능성이 높다. 그 경우 직접 학습한다.

### 4.4 운용상 남은 문제

- `./drive.sh mpc`의 기본 목표속도가 4.5 m/s다. Stanley처럼 `track.yaml`을 따르도록 수정해야 한다.
- `safety_node`에 리셋 경로가 없다(한 번 걸리면 재시작). 현재 기본 꺼짐.
- Ctrl+C 전체 경로를 실제 터미널에서 확인해야 한다.
- natnet 재연결을 재시도할 때 노드가 2개 남는 경우가 있었다.
- mocap이 WiFi를 쓴다. 프레임 유실이 잦으면 유선으로 옮기는 것을 검토한다.
